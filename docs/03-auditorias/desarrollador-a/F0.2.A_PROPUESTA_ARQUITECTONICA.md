**Fase:** F0.2.A (Propuesta técnica — Desarrollador A, pendiente de aprobación)  
**Restricción económica:** Presupuesto `$0 COP` para servicios externos, licencias y suscripciones.

---

## 1. Diagnóstico de viabilidad

La base de código actual (Java 21 + Spring Boot 4.1.1 + MySQL + Thymeleaf) permite evolucionar hacia un **monolito modular** de forma incremental sin reescritura ni migración a microservicios. El dominio actual es compacto y no presenta dependencias circulares.

El principio rector será: **el núcleo financiero determinista es la única fuente de verdad y debe funcionar al 100% aun si todos los proveedores externos (IA, Whisper, Telegram, Web Push) están caídos o sin cuota.**

---

## 2. Arquitectura modular objetivo

```text
com.gestorgastos.gestor_gastos
├── shared/                  # Excepciones base, Money/RoundingPolicy, Idempotency, Audit
├── security/                # SecurityFilterChain, CSRF, Auth, GrupoAccessEvaluator
├── identidad/               # Usuario, Auth clásica, Google OAuth, vinculación cuentas
├── grupos/                  # Grupo, MiembroGrupo, Invitaciones, enlaces/QR, invitados temp.
├── financiero/              # Gasto, PagoGasto, GastoParticipante, DeudaService, Liquidaciones
├── bandeja/                 # Bandeja Inteligente (borradores, OCR/ASR raw, confirmación humana)
├── ia/                      # Puertos de interpretación financiera, clasificación, deduplicación
├── recursos/                # ResourceManager (cuotas, colas, circuit breakers, fallback)
├── automatizaciones/        # Spring Scheduler: recurrentes, vencimientos, recordatorios, cierres
├── analitica/               # Presupuestos, comparativas, anomalías, metas, exportación PDF/Excel
├── conectividad/            # Adaptadores Telegram Bot API, Web Push, share target PWA
└── api/v1/                  # Controladores REST JSON para PWA / clientes desacoplados
```

## 3. Análisis de integración de componentes futuros (Presupuesto $0 COP)

| Componente | Rol en el sistema | Integración recomendada / Puertos | Riesgos y restricciones ($0 COP) |
|---|---|---|---|
| **ResourceManager** (`recursos/`) | Gobierna cuotas por proveedor/usuario, tokens, segundos de audio, concurrencia, reintentos y circuit breakers. | Interfaz `AiExecutionGateway` invocada por `ia/` y `bandeja/`. Registra consumo en BD (`uso_recursos`). | Evitar bloqueo de hilos web; degradar a modo manual si se agota cuota. |
| **Groq Free** (`ia/adapter/groq`) | Inferencia LLM rápida para extracción de gastos y copiloto. | Adaptador detrás de `LlmProviderPort` con timeouts y validación estricta de JSON. | Límites estrictos de RPM/TPM en capa gratuita; privacidad: minimizar PII enviada. |
| **Ollama** (`ia/adapter/ollama`) | Inferencia local sin costo por token ni salida de datos a terceros. | Adaptador alternativo detrás de `LlmProviderPort` (HTTP local). | Alto consumo de RAM/CPU en host (ej. Oracle Always Free); requiere fallback si no está disponible. |
| **Whisper / whisper.cpp** (`ia/adapter/asr`) | Transcripción de notas de voz a texto. | Interfaz `SpeechToTextPort` (local `whisper.cpp` o Groq Whisper Free). | Latencia en CPU; límites de tamaño de audio y duración. |
| **Motor de interpretación financiera** (`ia/`) | Convierte texto/OCR/transcripción en `PropuestaGastoDTO` estructurada. | **Nunca escribe en `financiero/`.** Entrega propuestas a `bandeja/` para validación determinista y confirmación humana. | Riesgo de alucinación o prompt injection; mitigado por validación determinista y confirmación obligatoria. |
| **Bandeja Inteligente** (`bandeja/`) | Recibe mensajes, imágenes, audios y comprobantes; crea borradores, deduplica y solicita confirmación. | Entidad `BorradorOperacion` con estados (`PENDIENTE_REVISION`, `CONFIRMADO`, `RECHAZADO`). Al confirmar, invoca `financiero/`. | Trazabilidad completa del origen (Telegram, PWA, web). |
| **Liquidaciones** (`financiero/`) | Registro de pagos entre miembros y confirmación bilateral; soporte a comprobantes Nequi/Daviplata. | Entidad `Liquidacion` integrada en `DeudaService`. Lectura de comprobante ≠ verificación bancaria real. | Requiere confirmación bilateral antes de afectar balances definitivos. |
| **Automatizaciones y Recurrentes** (`automatizaciones/`) | Gastos recurrentes, vencimientos, recordatorios, resúmenes semanales y cierres mensuales. | `Spring Scheduler` con bloqueos optimistas/idempotencia por ejecución (`ejecucion_programada`). | Evitar ejecuciones duplicadas si hay múltiples instancias. |
| **Presupuestos y Analítica** (`analitica/`) | Estadísticas, presupuestos, metas compartidas, anomalías, PDF/Excel. | Consultas agregadas de solo lectura sobre `financiero/` + librerías OSS (ej. OpenPDF, Apache POI). | Cuidado con consumo de memoria al exportar reportes grandes. |
| **Auditoría** (`shared/audit`) | Trazabilidad inmutable de eventos financieros y de seguridad. | Tabla `evento_auditoria` (`append-only`) alimentada por eventos de dominio Spring. | No almacenar secretos ni credenciales en payloads de auditoría. |
| **Telegram Bot API** (`conectividad/telegram`) | Bot privado y de grupos, vinculación segura por token temporal. | Adaptador webhook/long-polling que delega mensajes a `bandeja/` y comandos a `financiero/`. | No confiar en `chat_id` sin vinculación previa verificada con cuenta Partly. |
| **API reutilizable por PWA** (`api/v1/`) | Expone casos de uso en JSON para PWA instalable y Web Push. | Controladores `@RestController` sobre los mismos servicios de dominio que Thymeleaf. | Requiere CORS explícito, manejo estándar de errores (`ProblemDetail`) y auth segura. |

## 4. Orden recomendado de fases de evolución

1. **Fase F1 — Endurecimiento Base (Seguridad, Persistencia, Pruebas y Servicios Core):**
   - Incorporar `spring-boot-starter-security` (CSRF, `SecurityFilterChain`), Bean Validation y `@ControllerAdvice`.
   - Mitigar pre-hijacking en Google OAuth y reforzar política de contraseñas.
   - Incorporar Flyway/Liquibase, desactivar `ddl-auto=update`, añadir restricciones `UNIQUE`/`NOT NULL` y precisión `BigDecimal`.
   - Crear perfil `test` aislado (H2/Testcontainers) y suite de pruebas del núcleo financiero.
   - Extraer lógica de controladores hacia servicios de dominio e implementar idempotencia en creación de gastos.
2. **Fase F2 — Completitud del Núcleo Financiero y Contratos API:**
   - Edición/anulación segura de gastos, liquidaciones bilaterales, simplificación de deudas, optimización N+1, auditoría financiera y API `/api/v1/` para PWA.
3. **Fase F3 — Bandeja Inteligente y `ResourceManager`:**
   - Persistencia de borradores, control de cuotas, colas, circuit breakers y modo manual garantizado.
4. **Fase F4 — Inteligencia Artificial y Procesamiento Multimodal ($0 COP):**
   - Adaptadores Groq Free / Ollama / Whisper / OCR conectados exclusivamente a `bandeja/` bajo validación determinista.
5. **Fase F5 — Automatizaciones, Conectividad y Analítica:**
   - Gastos recurrentes (`Spring Scheduler`), Telegram Bot API, Web Push, presupuestos, analítica y exportación PDF/Excel.
