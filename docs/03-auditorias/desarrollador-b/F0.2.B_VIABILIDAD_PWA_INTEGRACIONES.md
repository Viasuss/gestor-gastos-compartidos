### 1.2 Diferencias de compatibilidad (Android vs. iOS vs. Escritorio)
- **Android (Chrome/Edge):** Soporte completo de instalación (`beforeinstallprompt`), Service Worker, Background Sync, Web Push y **Web Share Target** (permite recibir imágenes de comprobantes Nequi/Daviplata directamente desde el menú "Compartir" de Android hacia Partly).
- **iOS (Safari >= 16.4):** Permite instalación manual ("Añadir a pantalla de inicio") y Web Push **únicamente cuando la app está instalada en la pantalla de inicio** y el usuario otorga permiso tras interacción explícita. **No soporta** `beforeinstallprompt`, Background Sync ni Web Share Target en `manifest`. Requiere `<meta name="apple-mobile-web-app-capable">` y `apple-touch-icon` PNG (180x180).
- **Escritorio (Chrome/Edge/Firefox):** Chrome/Edge soportan instalación y Web Push; Firefox escritorio soporta Web Push pero no instalación nativa de PWA.

### 1.3 Estrategia segura de caché y sincronización (Sin exponer datos financieros)
1. **Regla de oro de privacidad:** El Service Worker **NUNCA** debe cachear respuestas HTML autenticadas (`/inicio`, `/mis-grupos`, `/grupo/**`), respuestas JSON financieras (`/api/v1/**`) ni encabezados de sesión en Cache Storage compartida.
2. **Cache Storage (`CacheFirst` / `StaleWhileRevalidate`):** Limitado exclusivamente a assets estáticos públicos y versionados (`/css/partly.css`, `/js/*.js`, `/img/*.png`, `/img/*.svg`, `/offline.html`).
3. **Datos financieros y borradores offline (IndexedDB):**
   - Si se habilita captura offline de borradores (ej. foto de factura o texto rápido sin señal), guardar en IndexedDB únicamente cola de borradores pendientes **cifrada o asociada al `userId` activo**, y **purgar IndexedDB y Cache dinámica al ejecutar `/logout`**.
   - Sincronización mediante `Idempotency-Key` (UUID generado en cliente) para evitar gastos duplicados en reintentos de red.
4. **Web Push (\$0 COP):** Implementable con estándar VAPID nativo (biblioteca Java `web-push` en backend y `PushManager` en navegador) sin servicios pagos como Firebase/OneSignal. El payload push debe evitar montos sensibles en pantalla bloqueada (ej. *"Tienes un nuevo gasto por revisar en Partly"*).

## 2. Evaluación de Telegram y WhatsApp (Diseño conceptual)

> **Nota:** Durante F0.2.B no se crean bots, no se solicitan credenciales ni se realizan llamadas a APIs externas.

### 2.1 Telegram Bot API (Viabilidad alta — \$0 COP)
- **Modo de privacidad inicial:** Mantener **Privacy Mode activado** (`BotFather /setprivacy -> Enable`) para que en grupos el bot solo reciba comandos (`/gasto`, `/balance`, `/resumen`) o menciones explícitas (`@PartlyBot ...`), protegiendo la privacidad de conversaciones cotidianas.
- **Flujos conceptuales:**
  1. **Vinculación segura de cuenta:** Usuario en Partly (`/perfil/telegram`) solicita código temporal de un solo uso (TTL 5–10 min) → envía `/vincular <CODIGO>` al bot privado → backend asocia `telegramUserId` con `usuarioId`.
  2. **Vinculación de grupos:** Usuario administrador del grupo en Partly genera token de grupo → añade el bot al grupo de Telegram y ejecuta `/vincular_grupo <TOKEN>` → backend valida membresía y enlaza `telegramChatId` con `grupoId`.
  3. **Registro por comando o lenguaje natural:** `/gasto 50000 mercado` o mención `@PartlyBot pagué 50mil en mercado con Ana` → backend (IA + `ResourceManager`) crea un **borrador en Bandeja Inteligente** (nunca escribe gasto directo sin confirmación).
  4. **Recepción de notas de voz e imágenes:** Usuario envía audio o foto de factura/comprobante → bot descarga archivo temporal (validando MIME/tamaño) → Whisper / OCR extrae propuesta → bot responde con **Inline Keyboard** (`[✓ Confirmar] [✎ Editar en web] [✕ Rechazar]`).
  5. **Consulta de balances, recordatorios y resúmenes:** `/balance` consulta resumen de deudas; tareas programadas envían recordatorios y resúmenes semanales respetando preferencias del usuario.
- **Contratos requeridos del Desarrollador A:**
  - Generación y validación de códigos de vinculación (usuario y grupo) con expiración.
  - Webhook seguro (`X-Telegram-Bot-Api-Secret-Token`) o Long Polling controlado.
  - Servicio de ingesta hacia Bandeja Inteligente y callback query handler con idempotencia.

### 2.2 WhatsApp (Viabilidad condicionada — \$0 COP)
- **Prohibición estricta:** No usar bibliotecas no oficiales (Baileys, whatsapp-web.js, etc.) para leer conversaciones privadas ni automatizar cuentas personales (riesgo de baneo y violación de términos/privacidad).
- **Uso gratuito seguro inmediato (Frontend):**
  - **Invitaciones y solicitudes de pago por enlaces `https://wa.me/?text=...` o Web Share API:** El usuario hace clic en *"Compartir por WhatsApp"* desde Partly y se abre su WhatsApp con el mensaje prellenado (enlace de invitación al grupo o resumen de deuda/solicitud de pago). Es 100% gratuito, oficial y no requiere API de WhatsApp Business.
- **Integración automatizada futura:** Condicionada a elegibilidad de Meta Cloud API, límites de conversaciones gratuitas de servicio y aprobación expresa en fases posteriores.

## 3. Evaluación de OCR y procesamiento de archivos (Facturas y comprobantes)

### 3.1 Opciones tecnológicas (\$0 COP)

| Tecnología | Ejecución | Ventajas | Limitaciones |
|---|---|---|---|
| **Tesseract.js** | Navegador (WASM) | Cero carga CPU/RAM en servidor; procesa imagen localmente sin enviar datos financieros a terceros. | Descarga inicial de modelo/datos de idioma (~2–15 MB); más lento en móviles de gama baja; menor precisión en recibos arrugados sin preprocesado. |
| **Tess4J (Tesseract OCR)** | Servidor Java | Control centralizado, integrable con OpenCV para preprocesado (escala de grises, binarización, deskew). | Consume CPU/RAM del servidor (crítico en Oracle Cloud Always Free); requiere binarios nativos Tesseract instalados. |
| **OpenCV** | Servidor / Cliente | Mejora drástica de precisión OCR en fotos con sombra o rotación. | Mayor complejidad de empaquetado nativo en Java. |

**Recomendación preliminar:** Arquitectura híbrida controlada por `ResourceManager`:
- Previsualización, recorte básico y validación de tamaño/MIME en frontend (`<input type="file" accept="image/*" capture="environment">`).
- Extracción determinista/OCR (Tess4J o Tesseract.js según capacidad) → creación de **borrador editable** en Bandeja Inteligente.
- **Regla financiera crítica:** La lectura OCR de un comprobante (Nequi/Daviplata) **nunca equivale a verificación bancaria real**. Solo prellena una propuesta de liquidación que requiere **confirmación bilateral humana** del receptor.

### 3.2 Puntos de integración UI y riesgos
- **Captura:** Input con cámara (`capture="environment"`) en móvil PWA y selector de archivo (`JPG`, `PNG`, `WEBP`, `PDF` máximo 1 página/5 MB) en escritorio.
- **Visualización y edición:** Vista lado a lado (imagen del recibo + formulario editable con campos detectados: comercio, monto total, fecha, ítems y nivel de confianza).
- **Riesgos a mitigar:**
  - *Seguridad de archivos:* Validar *magic bytes* en backend (no confiar en extensión o `Content-Type`), rechazar SVG/HTML activos para evitar XSS almacenado, eliminar metadatos EXIF (ubicación GPS del usuario).
  - *Privacidad y almacenamiento:* No almacenar comprobantes indefinidamente sin política de retención; servirlos únicamente bajo autorización de miembros del grupo (nunca URLs públicas predecibles).
  - *Prompt injection en documentos:* Texto extraído de facturas debe tratarse exclusivamente como datos no confiables, nunca como instrucciones.
